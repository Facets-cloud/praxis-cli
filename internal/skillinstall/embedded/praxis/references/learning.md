# Learning

For a concept question, explain the concept directly at the user's level. For
training, offer an interactive chapter: purpose, relationships, a compact ASCII
diagram and one concrete example. Distinguish the object, configuration layer,
operation and evidence of success. Do not turn every question into onboarding.

For Facets concepts consult the **raptor skill** route for that subject and
current official documentation where needed. Use source/help for version-specific
behavior; do not require the retired `docs-helper` skill. For Praxis concepts use
this package's relevant reference and deployed function descriptions.

Ask what remains unclear; offer another example or an optional quiz. Give a quiz
only if the user wants it. For a legacy chapter-style session, the earlier format
was five multiple-choice questions plus one short explanation, scored out of six
with feedback; retain it if that is the chosen teaching format, not as a hard
requirement for a simple explanation.

Questions should test distinctions that change decisions (e.g. override vs
effective value; schedule trigger vs run lookup; query vs build), not memorized
CLI spelling. Explain wrong answers without inventing platform behavior. Track
covered topics/feedback when useful and with the user's desired persistence;
don't silently publish quiz results or personal learning details to org memory.
Hands-on exercises follow [Onboarding](onboarding.md), with their own scope and
mutation boundaries. Teaching material is not permission to provision anything.
